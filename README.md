# 자동차 구매-출고-시공-수령 통합 MVP 프로토타입 (v6 기반, 신규 스펙 반영용 — mvp_v6)

> **이 저장소는 `mvp_v5`(원본, 수정하지 않음)를 복사해서 만든 별도의 독립 프로토타입입니다.**
> 목적은 실제 개발이 아니라 **네비게이션/화면 흐름 검증**이며, `vlp/car-lifecycle-cowork/docs/`의
> 신규 설계 문서(신차배송조회 서비스 스펙, UI 항목 스펙, 사용자/역할 모델 스펙)를 기준으로
> 화면을 순차적으로 갱신해나갈 예정입니다. git 이력도 `mvp_v5`와 완전히 분리된 독립 저장소입니다.

버전별 변경 이력은 [CHANGELOG.md](CHANGELOG.md)를 참고하세요(아래는 `mvp_v5`에서 복사해온 원본 이력입니다 — 이 저장소에서의 신규 변경사항은 상단에 별도로 추가하세요).

이 브랜치(`v6-service-split`)는 제조사(현대기아) 정책상 카마스터 개인이 온라인으로 별도 영업행위를 할 수 없다는 제약에 대응해, **신차인도서비스**와 **신차 케어 서비스**를 완전히 독립된 두 서비스로 분리한 개편판입니다. v5.2까지의 단일 파이프라인 구조는 `master` 브랜치에 그대로 남아 있습니다.

두 서비스는 이름만 다른 게 아니라 계약 당사자 자체가 다릅니다. 신차인도서비스 계약 안의 "출고 후 시공예정 여부"는 색상·트림처럼 카마스터-고객 계약에 딸린 단순 옵션(예상 정보)일 뿐이고, 실제 시공(신차 케어 서비스)은 그 옵션과 무관하게 고객이 시공사와 **별도로** 맺는 완전히 독립된 계약입니다 — 카마스터는 이 계약의 존재 여부를 미리 표시해둘 뿐, 시공사 선정·옵션 구성·가격 협상 어디에도 관여하지 않습니다.

## 서비스 구조

### ① 신차인도서비스 — 카마스터가 계약~차량 인도를 담당

1. **카마스터 찾기 (리서치 전용)**: 구매자는 앱에서 카마스터를 평점(전문성/응대속도/친절도) 기준으로 검색할 수 있지만, 이 화면에는 연결·요청 버튼이 없다 — 여기서 바로 연결하면 예전의 온라인 예약 흐름과 사실상 같아지기 때문이다. 실제 상담·계약 체결은 오프라인으로 진행한다.
2. **계약내역 등록 (고객)**: 이미 오프라인에서 체결된 계약(차량 모델·트림·색상·계약일자 + 카마스터 연락처 + 본인 정보)을 반드시 **고객이 먼저** 별도 화면("계약내역 등록하기")에서 그대로 입력한다(목록에서 고르지 않는다). "본인 정보(이름·연락처)"는 이미 로그인으로 신원이 확인된 상태이므로 로그인 정보로 자동 채워지며, 계약 당사자가 로그인한 사람과 다를 때만(예: 가족 명의 계약) 그 자리에서 수정하면 된다. 이 필드 조합 자체가 실제 계약서를 양쪽 다 들고 있어야만 맞출 수 있는 지문 역할을 한다. 입력한 연락처가 등록된 카마스터와 일치하면 그 카마스터의 대시보드에 승인 대기 건으로 바로 뜨고, 일치하지 않으면(아직 미등록 카마스터) 조회번호만 발급되어 나중에 자동 연결된다. 이 조회번호는 앱이 대신 전달하지 않는다 — 고객이 문자 등으로 직접 전달해야 한다.
3. **검토 및 승인 (카마스터)**: 등록된 카마스터는 별도 코드 입력 없이, 대시보드에서 고객이 등록한 계약 내용(차량정보·계약일자·고객정보)을 그대로 보고 실제 체결한 계약과 맞는지 확인한 뒤 승인한다 — 이때 출고 후 시공예정 여부·상담 메모만 추가로 입력한다. 이 시점부터 실제 처리가 시작된다. **아직 이 서비스에 등록되지 않은 카마스터**도 로그인 화면의 "조회번호로 첫 계약 등록"에서 같은 번호로 내용을 검토하고 가입과 승인을 한 번에 마칠 수 있다(가입과 동시에 자동 연결).
4. **계약 확인 (고객)**: 고객이 로그인해 카마스터가 승인한 내용을 최종 확인하면 계약이 확정된다.
5. **출고 요청 (고객 → 카마스터 2단계)**: 계약이 확정됐다고 곧바로 배송이 시작되지 않는다. **고객이 먼저** 최종 수령지(자택이든, 개인적으로 이용하려는 정비·시공업체든 무엇이든)를 정해 "차량 출고 요청하기"로 이제 차를 받고 싶다는 의사를 밝히면, 그걸 받은 **카마스터가** 비로소 공장에 출고를 의뢰한다 — 계약 등록이 온라인상의 소통 창구를 여는 것일 뿐, 그 자체로 출고를 트리거하지는 않는다는 원칙이다. 최종 수령지는 출고 요청 전까지 언제든 바꿀 수 있다.
6. **배송 및 인도 확인**: "출고 후 시공예정"이 아닌 건은 공장에서 최종 목적지까지 한 구간으로 곧장 배송된다. 시공예정인 건은 최종 목적지 전에 카마스터 지정업체를 먼저 들른다 — 도착하면 "시공중" 상태로 멈추고, 카마스터가 업체와 직접 소통해 시공완료를 확인해야 최종 목적지로 재배송이 시작된다. 이 지정업체 경유 구간은 철저히 카마스터-업체 간 별개 거래로 취급되어, 고객 화면에는 업체명이나 실시간 배송 상세 없이 "이동중" 정도의 안내만 노출된다(신차 케어 서비스와 무관). 최종 목적지에 도착해 **오너가 확인하는 순간, 신차인도서비스에서의 카마스터 역할이 끝난다.**

### ② 신차 케어 서비스 (시공, 신차인도서비스와 완전히 독립된 최상위 계약)

카마스터의 "출고 후 시공예정 여부"와는 완전히 무관하고, 신차인도서비스 예약(`data.reservations`)에 얹힌 하위 항목도 아니다 — `data.careOrders`라는 별개의 최상위 목록으로, 그 자체의 화면·번호·목록을 갖는다.

1. **"내 차량" 선택으로 시작**: 고객 화면의 독립된 랜딩("신차 케어 서비스")에서, 자신이 등록한 신차인도서비스 예약("내 차량") 중 하나를 골라 신청을 시작한다 — 출고 전이든 이미 받은 차든, 그 예약이 어느 단계에 있든 상관없다. 한 고객이 여러 대를 등록했다면 그중 아무 차나 고를 수 있다. 신청 시점에 그 차량의 기본정보(모델·트림·색상)와 고객정보를 스냅샷으로 복사해오므로, 이후 원본 예약과의 연결이 끊기거나(신차인도서비스가 이미 종료됨) 상태가 바뀌어도 시공사가 보는 정보는 그대로 유지된다.
2. **시공사 검색·선정**: 시공사는 카마스터와 달리 온라인에서 바로 검색·선택할 수 있다(평점 기반, 예약 없이 즉시 진행 가능).
3. **옵션 구성 및 견적 요청**: 기본 패키지 + 추가옵션(카탈로그에서 다중 선택) + 요청사항을 정하고, 온라인 즉시견적 또는 방문 후 협의 중 진행 방식을 고른다.
4. **견적 확인 → 계약 완료**: 시공사가 요청사항까지 반영해 최종 가격을 회신하면, 고객이 확인해야 계약이 완료된다(작업 착수 전 가격 확정).
5. **입고 확인 → 작업 → 검수 → 인도**: 차가 실제로 어떻게 왔는지(신차인도서비스 배송에 얹혀 왔든 고객이 직접 몰고 왔든)는 시공사가 상관하지 않는다 — 계약이 완료된 건에 대해 시공사가 스스로 "입고 확인"을 누르면 시공 흐름이 시작된다. 이후 작업 진행(사진 업로드 포함) → 청구액 정리 → 검수 요청 → 오너 단독 확인으로 출차 → 2차 배송 → 최종 수령까지 진행된다.
6. **사후처리**: 정찰제 확인(사전 견적 = 실제 청구액 비교) → 시공사 평가 → 포인트 적립.

신차인도서비스 계약확정 화면의 "신차 케어 서비스로 이동" 버튼은 해당 차량을 미리 선택해둔 채 이 독립된 신청 흐름으로 안내할 뿐이며, 그 서비스의 실제 진행은 이 흐름 안에서만 확인할 수 있다(신차인도서비스 상세화면에 자동으로 뜨지 않는다).

두 서비스는 완전히 독립적으로 포인트를 적립한다 — 신차인도서비스는 카마스터 평가, 신차 케어 서비스는 시공사 평가가 각각의 포인트 트리거다. 평가는 완료 즉시 남길 수도, "내 계약 확인" 이력에서 나중에 남길 수도 있다(강제하지 않음).

## 계약번호 체계

계약번호는 `SS-YYYYMM-NNNN` 형식이다(예: `10-202608-0001`). `SS`는 서비스유형(10=신차인도서비스, 20=신차 케어 서비스), `YYYYMM`은 앱에 등록(디지털화)된 연월, `NNNN`은 그 서비스유형 내 전체 누적 순번이다. 신차인도서비스(`data.reservations`, `seq` 카운터)와 신차 케어 서비스(`data.careOrders`, `careSeq` 카운터)는 "완전히 독립된 계약"이라는 원칙에 따라 각자 독립된 최상위 목록·번호·카운터를 갖는다(`requestCareOrder` 시점에 자체 번호를 발급받는다).

## 5개 역할 화면

| 파일 | 역할 | 할 수 있는 일 |
|---|---|---|
| `customer.html` | 구매자 | 카마스터 리서치(검색), 계약내역 등록(차량정보+카마스터 연락처 직접 입력), 계약 확인(내 계약이 2건 이상이면 계약번호·카마스터 이름·차종으로 좁혀보기), 신차 케어 서비스(독립 랜딩에서 "내 차량" 중 하나를 골라 시공사 선정·옵션구성·견적확인), 실시간 배송 확인, 사후처리(정찰제확인/평가/포인트) |
| `karmaster.html` | 카마스터 | (데모용 카드 클릭 로그인) 고객이 등록한 계약 내용을 검토 후 승인(코드 입력 없음), 미등록 카마스터는 조회번호로 내용 검토+가입+승인 동시 처리, 담당 고객 목록을 계약번호·이름·연락처로 실시간 검색, 출고 요청, 배송 모니터링 — 차량 인도 완료 시점에 역할 종료. 신차 케어 서비스에는 전혀 관여하지 않는다 |
| `shop.html` | 시공업체 | (데모용 매장 클릭 로그인) 견적 요청 수신·회신, 계약 완료 건의 입고 확인(스스로 판단), 작업→작업완료→검수요청, 사진 업로드, 청구액 입력, 2차 배송 시작 |
| `driver.html` | 배송기사 | 신차인도서비스 1차 배송 + 신차 케어 서비스 2차 배송을 한 목록에서 확인, 즉시 도착 처리 |
| `admin.html` | 관리자 (총괄) | 신차인도서비스/신차 케어 서비스 독립 탭 각각의 전체 현황 KPI, 계약 대리 등록 포함 **모든 단계를 대신 처리 가능** (데모 신속 진행용) |

`index.html`에서 5개 화면을 각각 새 창으로 열어 동시에 테스트할 수 있습니다.

## 실시간 배송 시뮬레이션 원리

- 배송이 시작되면 시작시각과 소요시간(데모 기준 8초)이 저장된다.
- 모든 화면이 0.5초마다 저장소를 읽을 때마다, 소요시간이 지난 배송 건을 자동으로 "도착" 처리한다 (`store.js`의 `_tick`).
- 배송기사·카마스터·관리자는 언제든 "즉시 도착 처리" 버튼으로 대기시간 없이 바로 도착시킬 수 있다 (데모 신속 진행용).

## 관리자(총괄) 계정의 역할

관리자는 데모의 신속한 진행을 위해 계약 대리 등록(카마스터 대신)부터 신차 케어 서비스 견적요청/회신/확인, 출고 요청, 배송 도착, 시공 단계 진행, 검수·수령 확인, 정찰제 확인, 평가 제출까지 전 과정을 대신 처리할 수 있습니다. 포인트는 계좌정보 입력 없이 즉시 적립되므로 관리자가 대신할 수 없는 단계는 없습니다.

## 실행 방법

```bash
npm install
npm run playwright:install   # 최초 1회, Chromium 바이너리 설치
npm run serve                # http://localhost:8000 에서 정적 서버 실행
```

## 자동 테스트 (tests/)

Playwright로 9가지 시나리오를 검증했습니다.

```bash
npm test   # 정적 서버 기동 + 9개 시나리오 순차 실행 + 결과 요약까지 한 번에 처리
```

개별 시나리오만 확인하려면 서버를 먼저 띄운 뒤 해당 파일만 실행합니다.


## 알려진 한계 (실제 서비스 설계 시 참고)

- 등록된 카마스터의 검증은 화면에 노출된 계약 필드(차량정보·계약일자·고객정보) 조합을 카마스터가 육안으로 대조하는 것에 의존합니다 — 시스템이 자동으로 필드 일치 여부를 검증하지는 않습니다. 미등록 카마스터용 조회번호는 만료 시간이나 재시도 제한이 없는 단순 6자리 난수입니다. 실제 서비스라면 유효시간·시도 횟수 제한이 필요합니다.
- 앱은 조회번호나 계약 내용을 대신 전달(문자 발송 등)하지 않습니다 — 고객이 직접 카마스터에게 전달해야 하며, 이는 "카마스터 개인 대상 온라인 접촉을 앱이 대신하지 않는다"는 원칙을 계약 시작 단계에도 일관되게 적용한 것입니다. 등록된 카마스터의 경우 별도 전달 없이 대시보드에서 확인할 수 있습니다.
- 배송 위치는 실제 GPS가 아니라 경과시간 기반 진행률로 시뮬레이션했습니다. 실제로는 배송기사 앱의 GPS 좌표를 지도에 표시해야 합니다.
- 카마스터/시공업체 로그인은 카드 클릭만으로 되는 데모용입니다. 실제로는 계정 인증이 필요합니다.
- 평점은 항목별 단순 평균만 계산합니다. 항목별 가중치를 반영한 통합점수 산정 방식은 다음 단계 과제로 남겨뒀습니다.
- 제공자별 고정 보너스 포인트(`bonusPoint`) 필드는 마련해뒀지만 값은 0으로 시작합니다 — 업체별 값을 입력하는 관리 화면은 이번 범위에 포함하지 않았습니다.
- 신차 케어 서비스의 "내 차량" 후보는 현재 신차인도서비스 예약 이력이 있는 차량으로만 한정됩니다(신차인도서비스 경험이 없는 차량을 수동으로 등록하는 기능은 없음). 순수 차량 등록 기능 추가는 다음 단계 과제입니다.
- 카마스터가 지정하는 협력업체(출고 후 시공예정, A 경로)는 선택적으로 업체명만 기록합니다(`karmasterShopName`) — 주소·진행상황까지 추적하는 데이터 모델은 없습니다. 이 관계는 철저히 카마스터-업체 간 별개 거래로 취급되어(신차 케어 서비스와 무관) 고객에게는 업체명이나 실시간 배송 상세가 노출되지 않고, 시공완료 여부도 카마스터가 오프라인 소통 후 직접 확인·대리 처리합니다.
- 포인트는 전화번호를 지갑 키로 사용하는 단순 모델입니다. 실제 서비스라면 회원가입 기반 계정 체계와 전화번호 검증(예: 인증문자)이 필요합니다.
- 데이터는 브라우저 localStorage에만 저장되므로, 실제 서비스에서는 백엔드(NestJS 등)와 DB, 실시간 통신(WebSocket 등)으로 대체되어야 합니다.
